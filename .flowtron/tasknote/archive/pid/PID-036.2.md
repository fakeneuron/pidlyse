**Discovery Notes:**

**Surface to extend:**
- `PortRegistry.swift` — `listeningPIDs(lsofOutput:) → Set<Int32>` (`:75`) and `parsePIDAndPort(_:ports:) → Int32?` (`:94`) already parse lsof lines but discard the port. The new `listeningPorts` mirrors `listeningPIDs` exactly (capture `effectivePorts` once, iterate lines) but accumulates `[Int32: Set<Int>]`. To avoid duplicating the column-parse logic, factor a `parseListenerLine(_:ports:) -> (pid, port)?` and have the existing `parsePIDAndPort` delegate (`?.pid`) — its public signature + behavior stay identical, all its tests still cover it.
- `ScanCore.swift` — `enumerate` returns `[ProcessItem]` (stray **candidates** only). `parentCommand(ofPPID:in:)` is a trivial `first { $0.pid == ppid }` over that set, returning the parent's `displayPath`. The parent is often NOT a candidate (a shell/launchd) → `nil` is the common, correct, gracefully-degrading result. `ProcessItem.displayPath` (`ProcessItem.swift:117`) is the established compact-command vocabulary.

**Assumptions (no clarifications needed — scope fixed by `.1`):**
- Port map value is `Set<Int>` (a PID can listen on >1 registered port — see the existing `listeningPIDs` dedupe test); UI sorts for display.
- "over the scan result set" = resolve against the `[ProcessItem]` candidate set literally (per `.1` Discovery note), not a full `ps` pid→command map. Parent-not-a-candidate degrades to `nil`; richer resolution is out of scope (would belong to a follow-up).
- launchd (`ppid == 1`) is excluded — orphans already surface via `ProcessItem.isOrphan`; a "child of launchd" hint is noise.
- No ScanEngine/MenuBarView wiring here — `.3` owns rendering + plumbing the port map to the view. `.2` ships the pure `public` resolvers + tests only.

**Tests live app-side:** PidlyseCore has no test target; all core tests run from `PidlyseTests/ScanEngineTests.swift` via `make test` (`@testable import Pidlyse` + `import PidlyseCore`). Mirror the existing `PortRegistry.listeningPIDs` / `parsePIDAndPort` test style.

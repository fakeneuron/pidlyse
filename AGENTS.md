# AGENTS.md — Pidlyse

Native macOS menu bar app. Full design in [`SPEC.md`](SPEC.md).

## Workflow

This project uses **flaitron** for task tracking. The canonical workflow contract lives at `.flaitron/core/SPEC.md` — read it before starting non-trivial work.

- Plans live in `.flaitron/PLAN.md`. Once `## Completed` outgrows its bound, closed rows rotate verbatim into an append-only `.flaitron/PLAN-ARCHIVE.md` (absent until the first rotation) — `.flaitron/core/SPEC/plan-filing.md` §"`## Completed` rotation".
- Tasknotes live in `.flaitron/tasknote/<TASK-ID>.md` while active and `.flaitron/tasknote/archive/<area>/<TASK-ID>.md` once closed.
- Start a task with `/ft-task <TASK-ID>`: it scaffolds the tasknote and drives Phase 1 Discovery before any code is written. Agents without `/ft-task` follow `.flaitron/core/SPEC/procedures/ft-task.md` (via `.flaitron/core/<platform>/procedures/ft-task.md` where one exists).
- `/ft-task` flags: `--debug` (hypothesis-first bug cadence), `--loop` (iterate Phase 2↔3 to a machine-checkable target — `.flaitron/core/SPEC/loop.md`), `--micro` (one `## ⚡ Notes` log in place of the phase checklists), `--fast` (suppresses conditional gates; `/ft-refactor`'s own `--fast` only skips its review pause), and `--unattended` (no operator present: gates park the tasknote instead of asking; never together with `--fast` — `.flaitron/core/SPEC/gate-postures.md` §"`--unattended` operator posture"). `/ft-close-epic` and `/ft-file-task` take `--unattended` too.
- Peer skills: `/ft-file-task [ID]` (`--park`, `--starter`), `/ft-open-epic`, `/ft-close-epic <ID>`, `/ft-refactor <target>` (plans only: a read-only survey, then an epic of children — it never edits source). Which shape fits which work: `.flaitron/core/SPEC/tasknote-selection.md` §"When to use a tasknote (and when not to)"; epics: `.flaitron/core/SPEC/epic.md`.
- Utilities: `/ft-seed-unattended` seeds `[unattended]` across an existing plan and never writes it unconfirmed (`.flaitron/core/SPEC/unattended-candidacy.md` §"Seeding an existing plan"); `/ft-update` bumps the flaitron pin.
- Filing a task, or a mid-flow decision that changes direction, runs a downstream-impact reconciliation scan against active PLAN entries; the plan is never rewritten without your confirm — `.flaitron/core/SPEC/tasknote-selection.md` §"Downstream-impact reconciliation".
- Optional, by hand: parallel epic children in worktrees (`.flaitron/core/docs/WORKTREES.md`), review-first specs that never file or scaffold (`.flaitron/core/templates/spec-template.md` → `.flaitron/specs/<slug>.md`), recurring heartbeat loops (`.flaitron/core/templates/loop-heartbeat-template.md`).
- Standard tasknotes (`/ft-task`) run the 4-phase workflow in serial order per `.flaitron/core/SPEC.md` §"The 4-phase workflow", followed by the post-closure protocol (commit + next-task suggestion). Do not skip phases once a tasknote is open — whether a change needs a tasknote at all is decided by `.flaitron/core/SPEC/tasknote-selection.md` §"When to use a tasknote (and when not to)".
- Each PLAN.md task line carries a `[model]` segment naming the model tier or name the task should run on end-to-end; adopters may use any short token. If the loaded model doesn't match, surface the mismatch before continuing. Contract: `.flaitron/core/SPEC/model.md` §"Model field".
- The `.flaitron/core/` submodule is read-only here. Edits go upstream to flaitron and arrive via deliberate version bumps — see `.flaitron/core/SPEC/versioning.md`. The pin is the submodule gitlink (`git -C .flaitron/core describe --tags`), also readable as the `**Version:**` line of `.flaitron/core/SPEC.md`; no project file restates it.

## Tech stack

- Swift + SwiftUI, macOS 14+, Apple Silicon target
- AppKit `NSStatusItem` bridge (`AppDelegate`) for the tray icon — hosts SwiftUI views; needed for right-click (`MenuBarExtra` exposes only left-click)
- `sysctl` / `ps aux` for process enumeration
- Xcode project, no backend

## Build

Open `Pidlyse.xcodeproj` in Xcode, ⌘R to run. App appears in menu bar only (`LSUIElement = YES`). Run the test suite from the command line with `make test` (the app scheme, then `swift test` for PidlyseCore). Build a Release app: `make build-release` (ad-hoc signed, output: `build/Release/Pidlyse.app`). Install to `/Applications`: `make install`. Package a DMG: `make dmg` (output: `build/Pidlyse.dmg`). Build the `pidlyse` terminal companion: `make build-cli` (output: `Packages/PidlyseCore/.build/release/pidlyse`); install to `/usr/local/bin`: `make install-cli`.

## Conventions

- All scan + classification logic lives in the `PidlyseCore` package (`ScanCore.swift`, `ProcessItem.swift`, `PortRegistry.swift`, `CwdResolver.swift`, `AncestryResolver.swift`, `OpenFilesResolver.swift`, `CustomRule.swift`, `IgnoreRule.swift`, `ScanHistory.swift`, `RespawnHistory.swift`, `Killability.swift`, `ScanPipeline.swift`, `ScanSettings.swift`, `StrayVerdict.swift`) — the shared core the app links; do not scatter it. App-side `ScanEngine.swift` owns only the timer / persistence / notification lifecycle and runs the one shared scan pipeline, `ScanPipeline.run(_:)` (PID-079.6: ports → container owners → `ScanCore.enumerate` → cwds → process table → scoped ignores), through its injectable `scanSource` (the default). The defaults suite, kill call, clean log, linger, and new-stray notifier are init seams too, so `PidlyseTests` drive the lifecycle with no real `ps` / `lsof` / signals (PID-078.3). Live system access belongs behind those defaults, never inline in `scan()` / `kill()`. The pure rolling-window CPU cache (`ScanHistory.swift`, PID-55.2) mirrors the same split: `ScanEngine` holds the single mutable instance, feeds it each scan, and exposes the "sustained low CPU" query — the quiet-CPU fact the stray verdict's Idle case reads, so through the verdict it now shapes the badge and the "Clean all" sweep (never the risk tier / bucket). The session-only respawn cache (`RespawnHistory.swift`, PID-62.2) is the third instance of that split: pure value type in core (command-signature normalization + windowed watches), `ScanEngine` owns the single mutable instance, arms it from the kill hook on a verified death and folds each scan into it, and exposes `isRespawner(_:)` — signal-only until PID-62.3 / PID-62.5 give it a surface. PID-62.3 is its first consumer and follows the same split: the pure `Killability` derivation + its one explanation sentence live in core, `ScanEngine.killability(_:)` folds the impure facts (scan-time owner uid, session-remembered `.unkillable` outcomes, `isRespawner`, ancestry/container attribution), and `MenuBarView` renders a badge in place of ✕ plus an inspector line. It is an overlay like 🔒 (never a bucket). The sweep predicate's shared base lives in core (`ScanPipeline.isProtected` / `isSweepable` + the Docker-aware `Killability.derive(for:…)`, PID-079.6) and the CLI calls it directly; `ScanEngine.isSweepable(_:)` folds it with the session facts (respawns, `EPERM` memory, kill phase) — the popover calls that rather than re-deriving it. The stray verdict (PID-086.2) is the fourth instance of the pure-core split: `StrayVerdict.derive` (session ended / duplicate / idle / running over a whole scan, from items + cwds + the tty-bearing process table; duplicate = exact command + cwd, not the respawn signature) lives in core with the quiet-CPU fact injected; `ScanEngine` publishes `verdicts` per scan (idle fed by `ScanHistory`), and the CLI feeds a single CPU sample. The popover (PID-086.4) partitions on `ScanEngine.verdict(_:)` — Likely strays by reason, Running folded by project — and the menu-bar badge and new-stray notifications count strays only; none re-derive the verdict. The reason display order (session ended, idle, duplicate, running) lives once in `StrayVerdict.displayOrder` (PID-089): the popover's sub-headers and `CLICore.listItems` both read it — never restate it, and place any new verdict case there. The sweep predicate is stray ∧ not high-risk ∧ not protected ∧ not port-bound ∧ killable (`ScanPipeline.isPortBound`, PID-088: a row or tree member listening on a registered port stays a per-row kill; consumers feed it the scan's `listeningPorts` and `portScanUnavailable` — PID-090: a port scan that returned no data counts every row as bound, so the sweep fails closed for that scan).
- The scan-relevant `UserDefaults` keys and their load live once in core (`ScanSettings.swift`, PID-079.7): `SettingsKey` names the five keys, `ScanSettings.load(from:)` reads them (the app's `ScanEngine.init` and the CLI's `Settings.load()` both call it), and `ScanEngine`'s `didSet` writes use `SettingsKey` too — never re-type a key string in a consumer. The strings are persisted user data; `ScanSettingsTests` pins them. App-only settings (`scanInterval`, `notificationsEnabled`) stay app-local.
- All subprocess spawning goes through the shared `Shell.run(_:_:timeout:)` primitive in `PidlyseCore` (`Shell.swift`) — one `Process`/`Pipe`/stdout-drain body for `ps`, `lsof`, and `docker`; do not hand-roll a new `Process()`. Callers own the *what* (which binary/args, how to parse) and pass that tool's `Shell.Budget` (`ps` 10s, `lsof` 20s, `docker` 20s); `Shell` owns the *how*, including the deadline. On expiry it SIGTERMs the child, SIGKILLs if it is still alive, and returns `("", false)` with partial stdout discarded, so a wedged scan still publishes and clears `isScanning`. `Shell.runReporting` is the same call plus `finished` (false on expiry / launch failure) for a caller that must tell "no answer" from "exited non-zero" (PID-090: the registered-port `lsof`).
- Docker plumbing lives in `PidlyseCore` (moved from app-side by PID-57.2 for the cli-companion): pure `docker ps` parsing + the `Container` model (`DockerCore.swift`, `Container.swift`) and the impure `docker` CLI access (`DockerService.swift` — path resolution, arg-building, `listContainers()`), which delegates the raw spawn to `Shell.run`. The app-side `DockerService+Async.swift` extension owns only the SwiftUI-facing async wrappers (background-queue shell-out, main-queue delivery). `KillCore`'s docker-stop path delegates to `DockerService` — keep all `docker` invocations there, don't scatter.
- Clean-log plumbing mirrors the same split (PID-53.2): the pure `CleanEvent` model + `CleanLog` aggregation (rolling-window stats + count-cap retention) live in `PidlyseCore` (`CleanEvent.swift`, `CleanLog.swift`), as does the shared disk I/O for `~/Library/Application Support/Pidlyse/clean-log.json` (`CleanLogFile.swift` — moved to core by PID-57.3 when the cli-companion became the second writer; one encoder/decoder so the formats can't drift). `append` re-reads under an exclusive `flock` on the sibling `clean-log.json.lock` so an overlapping app write and CLI write cannot drop an event. The app-side `CleanLogStore.swift` owns only the `@Published` binding + main-thread lifecycle: `record` enqueues `CleanLogFile.append` (re-read, merge, cap, save) off the main thread so the `flock` wait cannot stall the kill callback, then publishes a fresh load on the main thread; `reload()` runs when the popover opens; `ScanEngine` owns the kill-hook wiring (`recordCleaned`); both writers build events with the shared `CleanEvent(item:cwd:)`. `KillService.kill` reports a per-item `KillOutcome`; only `.confirmed` deaths are logged (privacy-first — no command line is persisted). Every kill trigger (row ✕, ⌘⌫, Clean all, `cleanAllSafe`) goes through `ScanEngine.kill(_:completion:)` (PID-62.5): it owns the per-row `KillPhase` lifecycle and the post-kill respawn check, and it returns a `KillReport`. Both of those are pure types in core (`KillFeedback.swift`) shared with the CLI, so every surface prints the same labels and summary line. Don't call `KillService.kill` from a view.
- Process-tree grouping lives once in `ScanCore.collapseTrees` (PID-62.4, generalizing PID-039's npm-wrapper merge): scanned parent→child chains fold into one row carrying `ProcessItem.members`, with root identity, representative label, and most-cautious tier. Every consumer (sweep, counts, clean log, respawn signatures, CLI) sees one logical unit. `KillCore.kill` kills the root and then each surviving member, and folds the results through `groupOutcome`; the owner fold is `Killability.groupOwnerUID`. Don't re-derive group membership elsewhere.
- Two classification buckets only: `safe` and `needsReview` — the kill-safety model inside `riskTier`. The `StrayVerdict` (PID-086.2) is not a bucket: it decides what reads as a likely stray and what "Clean all" sweeps (never a high-risk row). Never kill without explicit user action
- Port registry lives in `PortRegistry.swift` (in the `PidlyseCore` package); keep in sync with the canonical registry at `~/Code/natabula/docs/PORT-REGISTRY.md` when ports are added
- Kill flow is always SIGTERM first, SIGKILL fallback after 2 s — never skip the grace period. The kill path lives in `PidlyseCore` (`KillCore.swift`, PID-57.2): a synchronous, run-loop-free call (identity guards from PID-35.3, docker-stop routing, EPERM → `.unkillable`) shared with the cli-companion; app-side `KillService.swift` is only the thin async wrapper (background-queue call, main-queue callbacks). A kill reports what actually happened, never what was attempted (PID-62.2): after the SIGKILL fallback the process table is re-read, so `.confirmed` means verified gone (absent / recycled / zombie), `.survived` means still running under the same identity, `.notKilled` stays the "identity guard refused" answer, and `.unkillable` (PID-62.3) means EPERM — a foreign owner Pidlyse never escalates against. Add outcome cases here rather than letting a caller infer death from a signal having been sent.
- The `pidlyse` terminal companion (PID-57.3) is an `.executableTarget` (`Sources/PidlyseCLI/main.swift`) in the same package: a thin impure shell that reads the app's defaults domain (`com.fakeneuron.pidlyse`) for full rule parity and scans through the same core `ScanPipeline.run` call as the app (process table included — the stray verdict's session walk needs it, PID-086.2) — a new scan input lands once, in core. Its pure command grammar + table formatting live in core (`CLICore.swift`, tested from `PidlyseCoreTests`); hand-rolled arg parsing, zero external deps. `clean` sweeps the app's "Clean all" set (stray ∧ not high-risk, minus protected and foreign-owned) except respawners, which a one-shot CLI has no session memory of; `kill <pid>` accepts only scanned candidates; never kills without an explicit invocation.
- External-launcher integrations (PID-EPIC-58) all ride the one engine-side action layer — `ScanEngine.cleanAllSafe` + `sweepableStrays` SSOT + `rescan` (PID-58.2) — never re-derive the sweep set. The `pidlyse://` URL scheme routes through `AppDelegate.application(_:open:)` with the pure verb parse in `PidlyseCore.URLScheme` (mirrors `CLICore`); the Shortcuts/Spotlight bridge is two `AppIntent`s + an `AppShortcutsProvider` in `PidlyseApp.swift` (app-side glue, not core — they need the shared `ScanEngine` and must sit in the app target for AppShortcuts metadata extraction; kept there to avoid `project.pbxproj` surgery). Raycast integration is docs-only (`integrations/raycast/` scripts wrapping the installed CLI — no app code). AppleScript stays dropped (PID-35.1 "no NSAppleScript" baseline).

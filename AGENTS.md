# AGENTS.md — Pidlyse

Native macOS menu bar app. Full design in [`SPEC.md`](SPEC.md).

## Workflow

This project uses **flaitron** for task tracking. The canonical workflow contract lives at `.flaitron/core/SPEC.md` — read it before starting non-trivial work.

- Plans live in `.flaitron/PLAN.md`. Once `## Completed` outgrows its bound, closed rows rotate verbatim into a sibling `.flaitron/PLAN-ARCHIVE.md` (append-only; absent until the first rotation) — contract: `.flaitron/core/SPEC/plan-filing.md` §"`## Completed` rotation".
- Tasknotes live in `.flaitron/tasknote/<TASK-ID>.md` while active and `.flaitron/tasknote/archive/<area>/<TASK-ID>.md` once closed.
- Start a task with `/ft-task <TASK-ID>` (e.g., `/ft-task BE-014`). The slash command scaffolds the tasknote from the flaitron template and drives Phase 1 Discovery before any code is written. Contract-only agents without `/ft-task`: load `.flaitron/core/<platform>/procedures/ft-task.md` (if one exists for your platform) — it routes to the agent-neutral SOP at `.flaitron/core/SPEC/procedures/ft-task.md`.
- Other filing skills for non-task-shaped work: `/ft-micro-task <ID>`, `/ft-file-followup [ID]` (`--park [--low|--med|--fut|--high]`, `--starter`), `/ft-epic-discovery`, `/ft-close-epic <ID>`. Which shape fits which work: `.flaitron/core/SPEC/tasknote-selection.md` §"When to use a tasknote (and when not to)"; epic lifecycle: `.flaitron/core/SPEC/epic.md`.
- Filing a new task and mid-flow direction-changing decisions run a **downstream-impact reconciliation** scan so the plan stays cohesive as it grows: the new task/decision is checked against existing active PLAN entries for stale / contradictory / redundant overlap, and one reconcile action (merge / nest / edit / delete / leave) is proposed per impacted entry behind a user-confirm gate — the plan is never auto-rewritten. Contract: `.flaitron/core/SPEC/tasknote-selection.md` §"Downstream-impact reconciliation".
- For independent children of a multi-child epic, the optional worktree convention (location `<p>-worktrees/wt-<ID>/` alongside the project checkout, branch `wt-<ID>`, tasknote copy) lets you execute siblings in parallel isolated checkouts. Convention and the four-command start / end procedure: `.flaitron/core/docs/WORKTREES.md` — no skill; run it by hand or ask the agent to.
- For bugs and unexpected behavior, `/ft-task <TASK-ID> --debug` adds a hypothesis-first cadence (expected/observed → ranked hypotheses → minimal repro → re-verify) inside Phase 1 Discovery, plus a Phase 3 obligation to re-run that exact repro after the fix. Soft scaffolding, not a gate; composes with `--fast` in either order.
- When a task is driven by an orchestrator or headless session with **no operator present**, add `--unattended` (on `/ft-task`, `/ft-micro-task`, or `/ft-close-epic`): gates nobody is there to answer **park** the tasknote (`status: blocked` plus a machine-readable `park-reason:` code) instead of firing a banner into an empty session. Never pass it together with `--fast`. What it supersets, what it never relaxes, and the per-gate conversion map: `.flaitron/core/SPEC/gate-postures.md` §"`--unattended` operator posture". `/ft-file-followup --unattended` files a deferred step with no operator present (`.flaitron/core/SPEC/plan-filing.md` §"Filing commits").
- For converge-until-a-check-passes work (a suite going green, a metric crossing a threshold), `/ft-task <TASK-ID> --loop` runs the Phase 2↔3 execute→verify cycle as an inline loop against a machine-checkable Acceptance target. Loop budget, per-cycle relevance gate, and autonomy semantics: `.flaitron/core/SPEC/loop.md`. The recurring-maintenance (heartbeat) shape ships as `.flaitron/core/templates/loop-heartbeat-template.md`.
- To seed `[unattended]` across a plan that predates per-row candidacy: `/ft-seed` — walks every open PLAN.md row with the candidacy predicate, shows the candidates inside one review gate, and writes the marker only on the rows you keep. Flaitron never writes it unconfirmed. Contract: `.flaitron/core/SPEC/unattended-candidacy.md` §"Seeding an existing plan".
- To bump the flaitron version pin: `/ft-update` — shows the current→target changelog, moves the submodule, adds symlinks for any newly shipped skills, runs a smoke check, and stages the commit.
- Before filing, a design worked out in conversation can be captured as a review-first spec: copy `.flaitron/core/templates/spec-template.md` to `.flaitron/specs/<slug>.md` and fill its six sections. A spec never files a PLAN.md line or scaffolds a tasknote. When to reach for one: `.flaitron/core/SPEC/tasknote-selection.md` §"When to use a tasknote (and when not to)".
- `/ft-refactor <target> [--fast]` plans a behavior-preserving refactor of one named file, module, or subsystem: a read-only depth survey, then — on your go — an epic of starter-seeded children run through normal `/ft-task` cycles. It never edits source. When to reach for it: `.flaitron/core/SPEC/tasknote-selection.md` §"When to use a tasknote (and when not to)".
- Standard tasknotes (`/ft-task`) run the 4-phase workflow in serial order per `.flaitron/core/SPEC.md` §"The 4-phase workflow", followed by the post-closure protocol (commit + next-task suggestion). Do not skip phases once a tasknote is open — whether a change needs a tasknote at all is decided by `.flaitron/core/SPEC/tasknote-selection.md` §"When to use a tasknote (and when not to)". `/ft-micro-task` uses a lighter single-section ceremony in place of the full 4-phase flow.

## Tech stack

- Swift + SwiftUI, macOS 14+, Apple Silicon target
- AppKit `NSStatusItem` bridge (`AppDelegate`) for the tray icon — hosts SwiftUI views; needed for right-click (`MenuBarExtra` exposes only left-click)
- `sysctl` / `ps aux` for process enumeration
- Xcode project, no backend

## Build

Open `Pidlyse.xcodeproj` in Xcode, ⌘R to run. App appears in menu bar only (`LSUIElement = YES`). Run the test suite from the command line with `make test`. Build a Release app: `make build-release` (ad-hoc signed, output: `build/Release/Pidlyse.app`). Install to `/Applications`: `make install`. Package a DMG: `make dmg` (output: `build/Pidlyse.dmg`). Build the `pidlyse` terminal companion: `make build-cli` (output: `Packages/PidlyseCore/.build/release/pidlyse`); install to `/usr/local/bin`: `make install-cli`.

## Conventions

- All scan + classification logic lives in the `PidlyseCore` package (`ScanCore.swift`, `ProcessItem.swift`, `PortRegistry.swift`, `CwdResolver.swift`, `AncestryResolver.swift`, `OpenFilesResolver.swift`, `CustomRule.swift`, `IgnoreRule.swift`, `ScanHistory.swift`, `RespawnHistory.swift`, `Killability.swift`) — the shared core the app links; do not scatter it. App-side `ScanEngine.swift` owns only the timer / persistence / notification lifecycle and calls `ScanCore.enumerate(...)`. The pure rolling-window CPU cache (`ScanHistory.swift`, PID-55.2) mirrors the same split: `ScanEngine` holds the single mutable instance, feeds it each scan, and exposes the "sustained low CPU" query (signal-only — never touches the kill bar). The idle-dev-server consumer (PID-55.3) stays on the same split: the pure dev-mode-flag parse (`ScanCore.hasDevModeFlag`) lives in the core, `ScanEngine.isIdleDevServer` folds it with the sustained-low-CPU query + age + no-TTY, and `MenuBarView` surfaces the verdict as a single inspector reasoning line — still signal-only. The session-only respawn cache (`RespawnHistory.swift`, PID-62.2) is the third instance of that split: pure value type in core (command-signature normalization + windowed watches), `ScanEngine` owns the single mutable instance, arms it from the kill hook on a verified death and folds each scan into it, and exposes `isRespawner(_:)` — signal-only until PID-62.3 / PID-62.5 give it a surface. PID-62.3 is its first consumer and follows the same split: the pure `Killability` derivation + its one explanation sentence live in core, `ScanEngine.killability(_:)` folds the impure facts (scan-time owner uid, session-remembered `.unkillable` outcomes, `isRespawner`, ancestry/container attribution), and `MenuBarView` renders a badge in place of ✕ plus an inspector line. It is an overlay like 🔒 (never a bucket), and the sweep predicate lives once in `ScanEngine.isSweepable(_:)` — the popover calls it rather than re-deriving it.
- All subprocess spawning goes through the shared `Shell.run(_:_:)` primitive in `PidlyseCore` (`Shell.swift`) — one `Process`/`Pipe`/stdout-drain body for `ps`, `lsof`, and `docker`; do not hand-roll a new `Process()`. Callers own the *what* (which binary/args, how to parse); `Shell` owns the *how*.
- Docker plumbing lives in `PidlyseCore` (moved from app-side by PID-57.2 for the cli-companion): pure `docker ps` parsing + the `Container` model (`DockerCore.swift`, `Container.swift`) and the impure `docker` CLI access (`DockerService.swift` — path resolution, arg-building, `listContainers()`), which delegates the raw spawn to `Shell.run`. The app-side `DockerService+Async.swift` extension owns only the SwiftUI-facing async wrappers (background-queue shell-out, main-queue delivery). `KillCore`'s docker-stop path delegates to `DockerService` — keep all `docker` invocations there, don't scatter.
- Clean-log plumbing mirrors the same split (PID-53.2): the pure `CleanEvent` model + `CleanLog` aggregation (rolling-window stats + count-cap retention) live in `PidlyseCore` (`CleanEvent.swift`, `CleanLog.swift`), as does the shared disk I/O for `~/Library/Application Support/Pidlyse/clean-log.json` (`CleanLogFile.swift` — moved to core by PID-57.3 when the cli-companion became the second writer; one encoder/decoder so the formats can't drift). The app-side `CleanLogStore.swift` owns only the `@Published` binding + main-thread lifecycle and delegates load/save to `CleanLogFile`; `ScanEngine` owns the kill-hook wiring (`recordCleaned`). `KillService.kill` reports a per-item `KillOutcome`; only `.confirmed` deaths are logged (privacy-first — no command line is persisted). Every kill trigger (row ✕, ⌘⌫, Clean all, `cleanAllSafe`) goes through `ScanEngine.kill(_:completion:)` (PID-62.5): it owns the per-row `KillPhase` lifecycle and the post-kill respawn check, and it returns a `KillReport`. Both of those are pure types in core (`KillFeedback.swift`) shared with the CLI, so every surface prints the same labels and summary line. Don't call `KillService.kill` from a view.
- Process-tree grouping lives once in `ScanCore.collapseTrees` (PID-62.4, generalizing PID-039's npm-wrapper merge): scanned parent→child chains fold into one row carrying `ProcessItem.members`, with root identity, representative label, and most-cautious tier. Every consumer (sweep, counts, clean log, respawn signatures, CLI) sees one logical unit. `KillCore.kill` kills the root and then each surviving member, and folds the results through `groupOutcome`; the owner fold is `Killability.groupOwnerUID`. Don't re-derive group membership elsewhere.
- Two classification buckets only: `safe` and `needsReview` — never kill without explicit user action
- Port registry lives in `PortRegistry.swift` (in the `PidlyseCore` package); keep in sync with CLAUDE.md global port table when ports are added
- Kill flow is always SIGTERM first, SIGKILL fallback after 2 s — never skip the grace period. The kill path lives in `PidlyseCore` (`KillCore.swift`, PID-57.2): a synchronous, run-loop-free call (identity guards from PID-35.3, docker-stop routing, EPERM → `.unkillable`) shared with the cli-companion; app-side `KillService.swift` is only the thin async wrapper (background-queue call, main-queue callbacks). A kill reports what actually happened, never what was attempted (PID-62.2): after the SIGKILL fallback the process table is re-read, so `.confirmed` means verified gone (absent / recycled / zombie), `.survived` means still running under the same identity, `.notKilled` stays the "identity guard refused" answer, and `.unkillable` (PID-62.3) means EPERM — a foreign owner Pidlyse never escalates against. Add outcome cases here rather than letting a caller infer death from a signal having been sent.
- The `pidlyse` terminal companion (PID-57.3) is an `.executableTarget` (`Sources/PidlyseCLI/main.swift`) in the same package: a thin impure shell that reads the app's defaults domain (`com.fakeneuron.pidlyse`) for full rule parity and replicates `ScanEngine.scan()`'s pipeline order — keep the two pipelines in step when scan inputs change. Its pure command grammar + table formatting live in core (`CLICore.swift`, tested from `PidlyseTests`); hand-rolled arg parsing, zero external deps. `clean` sweeps the app's "Clean all" set (safe minus protected minus foreign-owned) except respawners, which a one-shot CLI has no session memory of; `kill <pid>` accepts only scanned candidates; never kills without an explicit invocation.
- External-launcher integrations (PID-EPIC-58) all ride the one engine-side action layer — `ScanEngine.cleanAllSafe` + `sweepableSafeItems` SSOT + `rescan` (PID-58.2) — never re-derive the sweep set. The `pidlyse://` URL scheme routes through `AppDelegate.application(_:open:)` with the pure verb parse in `PidlyseCore.URLScheme` (mirrors `CLICore`); the Shortcuts/Spotlight bridge is two `AppIntent`s + an `AppShortcutsProvider` in `PidlyseApp.swift` (app-side glue, not core — they need the shared `ScanEngine` and must sit in the app target for AppShortcuts metadata extraction; kept there to avoid `project.pbxproj` surgery). Raycast integration is docs-only (`integrations/raycast/` scripts wrapping the installed CLI — no app code). AppleScript stays dropped (PID-35.1 "no NSAppleScript" baseline).

- **Operator repro (this session):** "clicking on settings wheel just closes the window, nothing happens"; Cmd+, also no-ops. (Two prior tangents resolved first: a phantom `~/Code/pidly/Pidly.xcodeproj` stub from Xcode chasing the pre-rebrand path → deleted; and benign console noise — `_NSDetectedLayoutRecursion` (once-logged AppKit layout warning) + `fopen failed … errno = 2` (Metal shader-cache miss) — both OS-framework noise, not Pidlyse defects.)
- **Root cause (confirmed via git):** [[PID-022]] (commit `93f7425`) wired the gear to `@Environment(\.openSettings)` while the app still used SwiftUI `MenuBarExtra` — `MenuBarView` was inside the App scene graph, so the action was injected and worked. [[PID-023]] (commit `a086cb3`, same day) replaced `MenuBarExtra` with an AppKit `NSStatusItem` bridge: `AppDelegate` now hosts `MenuBarView` in a standalone `NSHostingController` (`AppDelegate.swift:35`), **outside** the App scene graph. `@Environment(\.openSettings)` is only populated by SwiftUI's App/Scene machinery, so in a manually-hosted hosting controller it resolves to the **default no-op** — `openSettings()` at `MenuBarView.swift:78` silently does nothing. PID-023 didn't re-test the gear→Settings path after the swap.
- **Source state:** `PidlyseApp.swift:10-14` declares `Settings { SettingsView(engine:) }` as the only Scene; app is `LSUIElement = YES` (accessory). `MenuBarView.swift:14` holds the dead `@Environment(\.openSettings)`; gear button at lines 77-83.
- **Fix approach:** open the `Settings` scene from `AppDelegate` (AppKit lives there per CLAUDE.md) via the responder chain: `NSApp.activate(ignoringOtherApps: true)` + `NSApp.sendAction(Selector(("showSettingsWindow:")), to: nil, from: nil)`. `activate` is required — an accessory app isn't active, so the window would open unfocused/behind. Pass a closure into `MenuBarView` instead of scattering `NSApp` calls into the SwiftUI view. macOS-14 target → `showSettingsWindow:` is the correct selector (PID-022's "unreliable" verdict was on the macOS-13 target without activation).
- **Drift check:** PLAN-line file citations all valid; the *characterization* ("strange content", chrome suspects) was wrong — corrected via Re-scope above.

**Implementation Notes:**

- **First attempt (reverted):** `AppDelegate.openSettings()` via `NSApp.sendAction(Selector(("showSettingsWindow:")))` + closure injection into `MenuBarView`. Failed on-device: macOS 14 no-ops that selector and logs `Please use SettingsLink for opening the Settings scene`. The `showSettingsWindow:` selector is a pre-Sonoma pattern.
- **Second attempt (reverted):** gear → `SettingsLink`. On-device the `Please use SettingsLink` warning disappeared (so it fired), but **no window appeared** — confirming the SwiftUI `Settings` scene does not present from this `LSUIElement` + `NSStatusItem` architecture (popover hosted in a standalone `NSHostingController` outside the App scene graph). None of the three sanctioned paths (env action / selector / SettingsLink) surface the scene from here.
- **Final fix (self-managed window):** stopped fighting the scene machinery. `AppDelegate.openSettings()` now builds an `NSWindow` hosting `SettingsView(engine:)` directly, `NSApp.activate(ignoringOtherApps:)`, then `makeKeyAndOrderFront` — reliable present + focus, no scene dependency. Window is retained (`settingsWindow`) so repeat opens reuse it; `isReleasedWhenClosed = false`. Closure re-injected into `MenuBarView` (gear `Button` calls it). The SwiftUI `Settings { SettingsView }` scene stays in `PidlyseApp` (satisfies the App scene requirement + native Cmd+, handling); the gear path is fully AppKit-owned per CLAUDE.md.

**Final Summary:**

The gear button / Settings stopped opening after [[PID-023]]'s MenuBarExtra→NSStatusItem migration moved `MenuBarView` into a standalone `NSHostingController` outside the App scene graph — where `@Environment(\.openSettings)` is a no-op. On macOS 14 the `showSettingsWindow:` selector also no-ops (redirects to `SettingsLink`), and `SettingsLink` itself fired but never surfaced a window from this out-of-scene-graph host. Resolved by presenting `SettingsView` in a self-managed AppKit `NSWindow` owned by `AppDelegate` (`openSettings()`: build/retain window → `NSApp.activate` → `makeKeyAndOrderFront`), with an explicit 360×620 content size (the `.grouped` Form has no intrinsic height) and `.resizable`. `AppDelegate.swift` + `MenuBarView.swift` (gear `Button` → injected closure); the SwiftUI `Settings` scene stays for Cmd+,. 67/67 tests pass; operator visually confirmed.

**Implementation Notes:**

The hop stays in `CleanLogStore`, the same split as `KillService` and `DockerService+Async`: background work, main-queue publish. `CleanLogFile.append` stays synchronous. The CLI and `CleanLogFileTests` still call it and still get the merged array back. `record` captures `fileURL` and `cap`, enqueues the append on a serial queue labeled `com.fakeneuron.pidlyse.clean-log`, and returns. The serial queue is the part those other hops do not need: two kill-hook records must append and publish in order.

The main-queue publish is a fresh `CleanLogFile.load`, so a `reload()` that already saw a newer disk snapshot is not overwritten by this append's older return value. `load` collapses a missing or unreadable file to `[]`. When that happens and the append returned a non-empty merge, the publish uses the merge, so a failed re-read does not blank a log this call just wrote. `reload()` and `init` stay synchronous. Neither takes the lock. No downstream-impact reconcile: the decision stays inside the store.

The peer test holds `flock(LOCK_EX)` on the sibling lock from another thread, asserts the holder actually took the lock, then calls `record` twice on the main thread. The release is a 0.6s timer, so a regression that appends inline fails the `< 0.25s` check instead of deadlocking against the holder. A short main-queue drain then asserts the published log is still empty. After the hold ends, both events publish in order and match disk. The existing CLI-merge test waits for the async publish. `reload()` is unchanged and still synchronous.

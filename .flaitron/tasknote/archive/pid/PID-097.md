# PID-097 | docker-stop-pid-collision

[← PLAN.md](../PLAN.md) · 🟢 In progress

## 🎯 Goal

Remove the `docker stop`-by-PID kill route so a `.docker` row whose host PID coincidentally matches a container's VM-side `State.Pid` can no longer stop an unrelated container; docker rows take the guarded POSIX kill path like every other row.

**Discovery Notes:**

- **Why it's wrong:** on macOS every Docker engine (Docker Desktop, Colima, OrbStack) runs containers in a Linux VM, so `docker inspect {{.State.Pid}}` is a VM-namespace PID. Container processes never appear in the host `ps` scan. The `.docker` rows Pidlyse does scan are `docker` CLI clients (`docker run`, `docker compose up`). Docker Desktop's own helpers classify as `nil` (`ScanCore.isDockerDesktopHelper`, PID-086.2) and are never rows; the external review corrected this note's first draft. Any `containerOwners[item.pid]` hit is a numeric coincidence. On that hit `docker stop <unrelated container>` runs, the start-time identity guard and the post-kill death check are skipped, `.confirmed` is logged, and the killability owner check is bypassed.
- **Archive:** PID-037.1 knew `State.Pid` is VM-internal and accepted it as "graceful-degrade … no false promise when it can't resolve". That reasoning covers *no match* but misses a *coincidental* match. The claim is falsified, so closure appends a ⚠️ pointer. PID-037.2 explicitly preserved the same match semantics. PID-063 kept the docker-stop routing when it trimmed the Containers tab, and PID-62.3 added the `routesViaDockerStop` owner bypass. All of this is reversed by this task.
- **After:** every docker row goes through `killPosix`: identity guard, SIGTERM → 2 s → SIGKILL, death check. A foreign-owned row is pre-flagged unkillable via its scan-time uid.

# PID-042 | shellout-dedup

[← PLAN.md](../PLAN.md) · 🟢 In progress · 🔗 [[PID-16.2]]

## 🎯 Goal

Consolidate the verbatim-duplicated `runShell(_:_:)` helper across `ScanCore.swift`, `PortRegistry.swift`, and `CwdResolver.swift` into a single shared `Shell` primitive in `PidlyseCore`, with the three call sites delegating.

## ✅ Acceptance

- [x] A single `public enum Shell { static func run(_ path:, _ args:) -> (output: String, ok: Bool) }` lives in `PidlyseCore`, carrying the stdout-drain-before-`waitUntilExit` invariant + the PID-35.2 stderr→`nullDevice` comment
- [x] The three `runShell(_:_:)` private copies in `ScanCore.swift`, `PortRegistry.swift`, `CwdResolver.swift` are deleted; their wrappers (`runPS`, `runLSOF`, `runLSOF(pids:)`) call `Shell.run(...).output`
- [x] `DockerService.run` keeps its `cliPath()` guard + `(output, ok)` signature but delegates the Process body to `Shell.run`; no duplicated Process/Pipe block remains app-side
- [x] No behavior change: stdout-only callers still get `""` on failure; `DockerService.run` still returns `("", false)` on launch failure / absent CLI
- [x] `make test` green

**Discovery Notes:**

- **PID-16.2** (shellout-helper) consolidated 5 sites → 3 local-per-file helpers; local placement was a deliberate PID-16.1 call **because ScanEngine/PortRegistry lived in the app target then** (separate modules). **PID-27.2** later moved them into `PidlyseCore`, so all three `runShell` now share one module — the original rationale for keeping them separate no longer holds, making a single shared helper natural.
- **PID-35.2** added stderr→`FileHandle.nullDevice` (deadlock fix) to all three core helpers **and** `DockerService.run`, and explicitly deferred consolidation. The 3-line stderr comment must survive into `Shell.run`.
- **Invariant to preserve:** `readDataToEndOfFile()` BEFORE `waitUntilExit()` (stdout drain); stderr → `nullDevice`.
- **Scope decision (AskUserQuestion → "all four"):** `public enum Shell.run -> (output, ok)` in `PidlyseCore`. Core callers take `.output`; `DockerService.run` keeps its `cliPath()` guard + `(output, ok)` return but delegates the Process body. Docker path-resolution/args/parsing stay in `DockerService` — only the generic Process dance is shared, so the CLAUDE.md "docker shell-out owned app-side" intent holds (DockerService still owns *when/with-what*; Shell owns *how*).
- `DockerService` already `import PidlyseCore`, so `public Shell` is directly reachable.
- **Phase 1→2 gate:** Discovery surfaced no significant deviation (the "all four" scope was floated by the task line and authorized by the operator) → skip 🛠️.

A local probe on this Mac found that `Process` does not leave the lock fd in the child (`ls /dev/fd` showed only the child's own fds), and that `LOCK_UN` plus `close` releases the lock even when a raw `fork`/`exec` child still holds the inherited fd. A `posix_spawn` without `POSIX_SPAWN_CLOEXEC_DEFAULT` does inherit a non-`CLOEXEC` lock fd, and `O_CLOEXEC` stops that. The filed change is still the open flag. It does not move `append` off the main thread; a peer that simply holds the lock can still block the kill callback for the length of that hold. That residual is outside this change and gets filed at closure.

Best practices: the lock fd already lives only in `acquireAppendLock`. The flag belongs on that `open`, not on a later `fcntl(F_SETFD, FD_CLOEXEC)`, which races with a spawn. No second lock implementation to fold into. Callers (`CleanLogStore.record`, the CLI `append`) stay as they are.

**Implementation Notes:**

The open in `acquireAppendLock` is the only place the lock fd is created. No other file sets close-on-exec, and `Shell.run` does not, because `Foundation.Process` closes stray fds on its own. Putting `O_CLOEXEC` on this `open` covers a `posix_spawn` that does not, which is the spawn a probe showed inherits the fd. A later `fcntl(F_SETFD)` would leave a window before the flag is set, so the flag is an argument to `open`. Callers, the JSON format, and the empty-append early return are unchanged. No downstream-impact reconcile.

The new test compiles a checker and `posix_spawn`s it with no file actions and no spawn attributes while `overlapDelayForTests` holds the lock, then asserts the child exits 0. `F_GETPATH` is the oracle because `/dev/fd` entries are devices here, not symlinks. A run without the flag fails with "child inherited the lock fd".

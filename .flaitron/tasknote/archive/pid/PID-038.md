**Discovery Notes:**

### Design decisions (two forks surfaced; both resolved via AskUserQuestion)

1. **cwd resolver mechanism → `lsof -p` (recommended, chosen).** One bulk `lsof -a -p <pids> -d cwd -Fpn` shell-out + a pure injectable `parseCwds(lsofOutput:)` parser in `PidlyseCore` — mirrors `PortRegistry` exactly, unit-testable like the rest of the core, no C pointer interop. Costs one extra subprocess spawn per scan (alongside the existing ps/lsof/docker spawns). The `proc_pidinfo(PROC_PIDVNODEPATHINFO)` syscall alternative (no spawn, faster) was offered but rejected for the testability/consistency win.
2. **Render scope → any row when resolvable (recommended, chosen).** No kind filter — consistent with the existing port/parent/owner hints, all of which render whenever their data resolves. The bare-interpreter rows the PLAN targets are the *motivating* case, not a hard filter.

### Explicit assumptions

- **Map stores display-ready (`~`-abbreviated) paths**, mirroring `containerOwners` (which stores the final slash-stripped name). The home-prefix collapse happens in the impure `processCwds` wrapper (`home: NSHomeDirectory()` is a runtime call); the pure `abbreviateHome(_:home:)` is injectable + unit-tested.
- **lsof field format:** `-Fpn` emits `p<pid>\n` then `n<path>\n` per process; `-a -d cwd` ANDs the selectors so only the cwd descriptor is reported (one `n` per process). Parser tracks the current PID from `p` lines.
- **`runShell` duplication:** `CwdResolver` carries its own private `runShell` (with the PID-35.2 stderr-drain comment), matching the existing duplicated copies in `ScanCore` + `PortRegistry`. Extracting a shared helper would touch both and is out of scope here.
- **No new SwiftPM manifest edit:** the package globs `Sources/PidlyseCore/`, so the new file is picked up automatically.
- **Map staleness on dismiss:** like `listeningPorts`, `dismiss(pid)` leaves stale `cwds` entries — harmless, the map is only read for rows still present.

Discovery surfaced no significant deviation (both clarifications confirmed the planned approach via the recommended options; no file/approach/root-cause change) → **skip 🛠️**.

### Phase 3 visual-confirm addendum (two render iterations)

**Iteration 1 — render location.** The first cut rendered the cwd only inside the ⓘ expansion (`in <cwd>`). The operator's visual confirm rejected it: the always-visible row line still showed the redundant bare `npm`/`node`, so the owner stayed unidentifiable at a glance. **Re-scoped within the same goal:** promote the cwd to the row's primary descriptor line (`rowDescriptor`), falling back to `displayPath` when unresolvable.

**Iteration 2 — project label, not raw path.** The full `~/Code/<project>` path on the row truncated mid-string (`~/Co...ecks`), unreadable, and the operator wanted the *project/repo name* rather than the literal folder. **Refined (still same goal):**
- `CwdResolver` now derives a short `projectLabel` from the enclosing **git repo root** (injectable `findGitRoot` walk): `bidviz` at the root, `bidviz/frontend` in a subfolder, leaf-folder name when not in a repo. Git-root detection (vs. stripping a hardcoded `~/Code/` prefix) is the non-error-prone way to identify the project, per the operator's concern.
- The map type changed `[Int32: String]` → `[Int32: ProcessCwd]` (`label` for the row + `~`-abbreviated `fullPath` for a `.help` hover tooltip, so the full path is recoverable despite truncation).
- Row truncation switched `.middle` → `.tail` so the repo name (front of the label) always stays visible.

Both iterations stay inside PID-038's stated goal ("the project folder ... so the owner is identifiable"). Adjacent to [[PID-039]] (npm-surface-dedup, a grouping/nesting concern) but complementary — no PLAN reconciliation needed.
